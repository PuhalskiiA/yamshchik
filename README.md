# Yamshchik

Сервис технологических email-рассылок: принимает письмо по HTTP, сохраняет его в очередь и отправляет по SMTP.

## Что нужно

- JDK 25
- Docker с Compose — для PostgreSQL, хранилища вложений MinIO и почтового сервера-ловушки

Maven ставить не нужно, в проекте есть обёртка `mvnw`.

## Запуск

Всё в контейнерах, одной командой (первая сборка образа идёт несколько минут):

```bash
docker compose --profile app up -d --build --wait   # приложение на http://localhost:8080
```

Или окружение в контейнерах, а приложение из исходников — так удобнее при разработке:

```bash
docker compose up -d --build --wait   # PostgreSQL, MinIO, почтовые серверы, Kafka, Prometheus и Grafana
./mvnw spring-boot:run        # приложение на http://localhost:8080
```

Из IntelliJ IDEA — готовая конфигурация запуска «Yamshchik (local)» (файл `.run/Yamshchik (local).run.xml`).

Все три способа используют профиль `local` и занимают порт 8080, одновременно их не запускать.

Схема БД создаётся при старте приложения (Liquibase).

Письма уходят через свой почтовый сервер стенда (Postfix и Dovecot, `stand/mailserver`): SMTP на 2525, IMAP на 1143.
Сервис отправляет под учётной записью `noreply@yamshchik.test` / `yamshchik-secret` и из её же ящика читает
отчёты о доставке. Письма на домен `yamshchik.test` сервер кладёт в свои ящики (местный получатель —
`user@yamshchik.test` / `user-secret`), на остальные домены пересылает в Mailpit: http://localhost:8025.

Вложения лежат в MinIO в бакете `yamshchik`; он создаётся вместе с контейнером. Консоль: http://localhost:9001,
учётная запись `yamshchik` / `yamshchik-secret`.

События о доставке публикуются в Kafka (`localhost:9092`), топик `yamshchik-delivery-events`.

Показатели собирает Prometheus (http://localhost:9090) — и с приложения на хосте, и с приложения в контейнере.
Дашборд «Ямщик: отправка и доставка» открывается в Grafana сразу: http://localhost:3000, вход не нужен.

### Стенд для опытов с темпом

Заглушка почтового сервера получателя (`stand/smtp-stub`): принимает письма в никуда, ограничивает темп и считает
письма, полученные повторно с тем же `Message-ID`. SMTP — порт 2526, настройки и показатели — http://localhost:8026:

```bash
curl -X PUT "http://localhost:8026/config?rate=2&burst=1&penalty=0"   # предел 2 письма в секунду
curl http://localhost:8026/metrics                                     # принято, отклонено, повторы
curl -X POST http://localhost:8026/reset                               # обнулить счётчики
```

Превышение предела получает `451 4.7.1` на команду `MAIL`; `penalty` — на сколько секунд после превышения
отказывать во всём. Как сервис подключается к серверу получателя:

- **напрямую в заглушку** — регулятор сервиса сам видит ответы сервера:
  `SPRING_MAIL_HOST=localhost SPRING_MAIL_PORT=2526 ./mvnw spring-boot:run`;
- **через свой Postfix** — темпом управляет почтовый сервер (базовая линия):
  `MAILSERVER_RELAYHOST='[smtp-stub]:2525' MAILSERVER_RATE_DELAY=1s docker compose up -d mailserver`.

Остановить окружение: `docker compose down`, вместе с данными БД и вложениями — `docker compose down -v`.

## Проверка

Письмо с текстом, HTML, встроенной картинкой и вложением. Каждое вложение описывается в `attachmentOptions`
с контрольной суммой SHA-256 содержимого (`sha256sum logo.png` в Git Bash, `Get-FileHash logo.png` в PowerShell —
в нижнем регистре):

```bash
cat > email.json <<EOF
{
  "to": [{"address": "user@example.com", "name": "Иван Иванов"}],
  "subject": "Отчёт готов",
  "body": {
    "text": "Текстовый вариант",
    "html": "<p>HTML-вариант <img src=\"cid:logo\"></p>"
  },
  "attachmentOptions": [
    {"filename": "logo.png", "sha256": "$(sha256sum logo.png | cut -d' ' -f1)", "disposition": "INLINE", "contentId": "logo"},
    {"filename": "report.pdf", "sha256": "$(sha256sum report.pdf | cut -d' ' -f1)"}
  ]
}
EOF

curl -X POST http://localhost:8080/api/v1/emails \
  -F "email=@email.json;type=application/json" \
  -F "attachments=@logo.png;type=image/png" \
  -F "attachments=@report.pdf;type=application/pdf"
```

В ответе — список `emails` с идентификатором и статусом `ACCEPTED` каждого принятого письма.

Файл, который сервис уже принимал, можно не прикладывать: достаточно описания с той же суммой — вложение возьмётся
из хранилища, второй раз оно туда не загружается. Если такого вложения нет (никогда не присылалось или удалено
уборкой), ответ — `409` со списком недостающих сумм в `missingAttachments`: повторите запрос с этими файлами.
Присланный файл сверяется с заявленной суммой, расхождение — `400`; файл без описания — тоже `400`.

Персональная отправка — `"personal": true` в запросе: каждому получателю из `to` уходит отдельное письмо,
в ответе их столько же, сколько получателей. `cc` и `bcc` в этом режиме дают `400`.

Состояние письма:

```bash
curl http://localhost:8080/api/v1/emails/{id}
```

Статусы письма: `ACCEPTED` → `SENDING` → `SENT` либо `FAILED`. После временного отказа письмо уходит в `DEFERRED`
и ждёт следующей попытки (`nextAttemptAt`); после постоянного отказа или последней попытки — в `FAILED`.
`SENT` значит «почтовый сервер принял»; что было дальше, видно по каждому получателю в `deliveries`.

Доставка каждому получателю (`deliveries`), включая копии и скрытые копии:

| Статус | Значение |
|---|---|
| `PENDING` | Сервер ещё не принял письмо для этого получателя |
| `SENT` | Принял, отчёт о доставке не пришёл; отчёт о задержке статус не меняет |
| `DELIVERED` | Отчёт о доставке или о передаче дальше (`reportAction`: `DELIVERED`, `RELAYED`, `EXPANDED`) |
| `UNDELIVERED` | Отчёт об окончательном отказе, отказ при отправке или исчерпаны попытки |

Отчёт об отказе по временной причине (`4.x.x`) возвращает доставку в `PENDING`, а письмо — в `DEFERRED`:
при следующей попытке письмо уходит только тем получателям, по которым пришёл отказ; в заголовках остаются все.
Письма одного запроса объединены общим `batchId`.

По каждой доставке, ставшей `DELIVERED` или `UNDELIVERED`, в Kafka публикуется событие (JSON, ключ — идентификатор
письма): `eventId`, `batchId`, `emailId`, `recipient`, `outcome`, `action`, `status`, `diagnostic`, `occurredAt`.
Событие может прийти повторно — потребитель отбрасывает повторы по `eventId`.

Если по письму с приоритетом `HIGH` отчёт не пришёл за `REPORT_IMPORTANT_TIMEOUT`, в лог пишется ошибка
`Incident: no delivery report for important email …`; повторно письмо при этом не отправляется.

## Настройки

Настройки разделены на два файла в `src/main/resources`:

- `application.yaml` — общее для всех стендов: поведение очереди, повторы, лимиты приёма, метрики;
- `application-local.yaml` — то, что зависит от стенда: адреса и учётные записи БД, почтового сервера
  и хранилища вложений, отправитель писем (`yamshchik.sender`). Значения рассчитаны на `compose.yaml`.

Отправитель у всех писем один и в запросе не задаётся: адрес и отображаемое имя берутся из `yamshchik.sender`.

Без профиля приложение не стартует: адресов служб в общем файле нет. Для другого стенда нужен свой
`application-<стенд>.yaml` или переменные окружения Spring (`SPRING_DATASOURCE_URL`, `SPRING_MAIL_HOST`,
`YAMSHCHIK_STORAGE_ENDPOINT` и т. д.) — так сделано для приложения в контейнере.

Поведение переопределяется переменными окружения:

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `RETRY_POLICY` | `exponential` | Повторы: `exponential` — только временные отказы, пауза удваивается; `fixed` — любой отказ через одну и ту же паузу |
| `RETRY_MAX_ATTEMPTS` | `5` | Сколько всего попыток, считая первую |
| `RETRY_INITIAL_DELAY` / `RETRY_MAX_DELAY` | `PT30S` / `PT1H` | Пауза перед второй попыткой и предел её роста |
| `ATTACHMENT_STORAGE` | `s3` | Где лежат вложения: `s3` — объектное хранилище; `filesystem` — каталог на диске экземпляра; `kafka` — топик Kafka |
| `DISPATCH_WORKERS` | `4` | Сколько обработчиков одновременно отправляют письма |
| `REPORT_IMPORTANT_TIMEOUT` | `PT30M` | Сколько ждать отчёта о доставке письма с приоритетом `HIGH`, прежде чем записать инцидент |
| `RATE_LIMIT_STRATEGY` | `none` | Ограничение темпа: `none` — без ограничения; `fixed` — постоянный темп; `aimd` — темп растёт, пока сервер принимает, и падает вдвое, когда сервер просит сбавить |
| `RATE_LIMIT_RATE` | `10` | Темп, писем в секунду: постоянный для `fixed`, начальный для `aimd` |
| `RATE_LIMIT_URGENT_SHARE` | `0.2` | Доля темпа, гарантированная срочным письмам (приоритет `HIGH`) |
| `RATE_LIMIT_MIN_RATE` / `RATE_LIMIT_MAX_RATE` | `0.05` / `100` | Пределы темпа для `aimd` |
| `INTERRUPTED_WAIT` | `PT2M` | Сколько письмо, отправка которого прервалась, ждёт отчёта о прерванной попытке, прежде чем уйти снова |
| `ATTACHMENT_STORAGE_CAPACITY` | `10GB` | Объём хранилища, отведённый под вложения; при заполнении на 75 % начинается уборка |
| `DISPATCH_QUEUE` | `postgres` | Очередь отправки: `postgres` — в таблице писем, переживает рестарт; `memory` — в памяти процесса, при рестарте ждущие письма остаются в `ACCEPTED` и не отправляются |

Интервал опроса очереди — `yamshchik.dispatch.poll-interval` в `application.yaml`. Там же срок аренды
`yamshchik.dispatch.lease` (5 минут): письмо, итог отправки которого за это время не записан, берётся в отправку снова.
Пока письмо отправляется, аренда продлевается — долгая отправка большого письма его не теряет.
Если аренда всё же истекла (обработчик упал посреди отправки), письмо сразу не повторяется: сервер мог успеть
его принять. Оно ждёт отчёта о прерванной попытке `INTERRUPTED_WAIT` (2 минуты); пришёл отчёт — повтора нет,
не пришёл — письмо уходит снова.

**Классы трафика.** Письма с приоритетом `HIGH` — срочные: они берутся из очереди первыми, и им гарантирована
доля темпа `RATE_LIMIT_URGENT_SHARE`. Массовые занимают эту долю, только пока срочных нет.

**Уборка вложений** (`yamshchik.storage.cleanup`, раз в 10 минут). Удаляются только вложения писем, которые больше
не будут отправляться: все письма с этим вложением в `SENT` или `FAILED`. Вложения писем, ещё ждущих отправки,
не удаляются никогда.

- **По сроку** — вложения писем, завершённых больше 3 дней назад, удаляются при каждом запуске.
- **По заполненности** — если хранилище заполнено на 75 % и больше, удаляются вложения недавно завершённых писем,
  от давних к свежим, пока заполненность не опустится ниже порога. Если удалять больше нечего, а места всё равно
  мало, в лог пишется ошибка.

Из Kafka отдельное вложение удалить нельзя, там уборка не работает.

Отказы для проверки повторов задаются в Mailpit — он стоит за своим почтовым сервером стенда, поэтому его отказ
приходит сервису отчётом о доставке. Например, временный отказ на каждого получателя:
`curl -X PUT http://localhost:8025/api/v1/chaos -d '{"Recipient":{"ErrorCode":451,"Probability":100}}'`;
сброс — тот же запрос с `{}`. Сроки очереди своего сервера сжаты: отчёт о задержке приходит через минуту,
окончательный отказ — через три.
Ограничения на письмо — там же, в `yamshchik.intake`: размер после кодирования (25 МБ), число получателей (100) и вложений (10).
Превышение размера даёт `413`, остальные нарушения — `400`.

## Метрики

`GET /actuator/prometheus` — показатели в формате Prometheus, `GET /actuator/health` — состояние сервиса.

| Метрика | Что показывает |
|---|---|
| `yamshchik_emails_accepted_total` | Писем принято |
| `yamshchik_dispatch_attempts_seconds` | Попытки отправки и их длительность; метки `outcome` (sent, deferred, failed) и `reply` (accepted, 4xx, 5xx, none) |
| `yamshchik_emails_delivery_time_seconds` | Время от приёма письма до приёма его почтовым сервером |
| `yamshchik_emails_by_status` | Сколько писем в каждом статусе; метка `status` |
| `yamshchik_emails_waiting` | Сколько писем ждут отправки; метка `class` (urgent, bulk) |
| `yamshchik_dispatch_rate_limit` | Текущий предел темпа, писем в секунду |
| `yamshchik_deliveries_by_status` | Доставок получателям в каждом статусе |
| `yamshchik_deliveries_report_time_seconds` | Время от приёма письма сервером до отчёта о доставке; метки `action`, `class` |
| `yamshchik_deliveries_incidents_total` | Инцидентов: отчёт о важном письме не пришёл вовремя |
| `yamshchik_events_unpublished`, `yamshchik_events_unpublished_age_seconds` | Сколько событий ждут публикации в Kafka и возраст старейшего |
| `yamshchik_attachments_stored_bytes` | Сколько занимают вложения в хранилище |
| `yamshchik_attachments_deleted_total`, `yamshchik_attachments_deleted_size_bytes_total` | Удалено уборкой; метка `forced` — удалено из-за нехватки места, а не по сроку |

У попыток отправки и времени доставки есть ещё метки `class` (urgent, bulk) и `signal` — что ответ сервера значит
для регулятора: `accepted`, `throttled` (просит сбавить темп), `failed` (отказ не из-за темпа).

## Сборка

GitHub Actions, `.github/workflows/ci-cd.yml`. На каждый push в любую ветку: сборка, тесты (`mvnw verify`)
и образ, собранный с этой ветки. Образ публикуется в Docker Hub как `w8404/yamshchik` с тегами
`<ветка>` (косая черта в имени заменяется дефисом) и `sha-<коммит>`; сборка с `main` получает ещё и тег `latest` —
его и забирают для развёртывания: `docker pull w8404/yamshchik:latest`.

Тот же пайплайн можно запустить вручную для любой ветки: Actions → CI/CD → Run workflow.

Учётные данные Docker Hub задаются в настройках репозитория, Settings → Secrets and variables → Actions:

| Имя | Где | Значение |
|---|---|---|
| `DOCKERHUB_USERNAME` | вкладка Variables | Логин Docker Hub с правом записи в `w8404/yamshchik` |
| `DOCKERHUB_TOKEN` | вкладка Secrets | Пароль или токен доступа Docker Hub с правом записи |

## API

Контракт описан в `src/main/resources/openapi/yamshchik-api.yaml` и является источником истины:
интерфейсы контроллеров и DTO генерируются из него при сборке. Менять API нужно начиная со спецификации.

## Структура

```
domain/        модель письма и переходы статусов
application/   сценарии и порты (port/in — входящие, port/out — исходящие)
adapter/in/    REST и планировщик очереди
adapter/out/   PostgreSQL, очередь в памяти, хранилища вложений, SMTP, ящик отчётов (IMAP), события (Kafka)
config/        конфигурации, настройки (properties), исключения (exception)
```

Открытые задачи и принятые решения — в `BACKLOG.md`.
